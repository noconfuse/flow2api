# 100+ Google Flow 账号热池/冷池运维方案

这份方案面向如下目标：

- 你有 100+ 个 Google Flow 账号
- 想对外只暴露一个统一 API 服务
- 不想长期手工复制 `session_token`
- 希望账号失效后能低成本恢复
- 希望后续扩容到更多账号时架构仍然稳定

本方案默认使用以下角色：

- `Flow2API`：统一 API 网关、账号池调度中心
- `浏览器 Profile 农场`：维护账号长期登录态
- `Token Updater 插件`：把最新 `session_token` 自动推回 `Flow2API`
- `热池`：当前在线提供服务的核心账号
- `冷池`：备用账号，平时不参与高频调度

## 总体架构

推荐按下面的链路部署：

```text
业务系统 / 外部调用方
        |
        v
    反向代理 / WAF
        |
        v
      Flow2API
        |
        +--> 热池账号调度
        |
        +--> 冷池账号登记
        |
        +--> 插件 token 回传入口
               ^
               |
      浏览器节点 A / B / C
               |
               +--> 每个账号一个独立 profile
               +--> 每个 profile 绑定固定代理
               +--> 安装 Token Updater 插件
```

核心思想：

- `Flow2API` 只负责统一 API、账号状态管理、调度和监控
- 真正长期维护登录态的是浏览器 profile，而不是人工导出的 `tokens.txt`
- `session_token` 变化后由插件自动上报，不依赖人工复制
- 热池负责承载流量，冷池负责故障替补和扩容

## 为什么要热池/冷池分层

100+ 账号全部同时作为高活跃账号，会带来几个现实问题：

- 浏览器 profile 数量太多，维护成本高
- 代理、验证码、风控同时放大
- 单个账号偶发失效会让排障成本暴涨
- 你未必真的需要 100 个号同时提供服务

所以推荐分层：

- `热池`：10 到 30 个账号，长期在线、固定代理、重点维护
- `冷池`：其余账号，登记在册，只在热池不足时接管

对大多数场景，一个 20 账号热池已经能明显降低维护成本。

## 推荐分组

以 120 个账号为例：

- `热池 A 组`：8 个
- `热池 B 组`：8 个
- `热池 C 组`：8 个
- `冷池 D 组`：24 个
- `冷池 E 组`：24 个
- `冷池 F 组`：24 个
- `冷池 G 组`：24 个

这样做的好处：

- 热池可以分批轮换维护
- 冷池可以按组补位
- 发生代理问题时，能快速定位到某一组

## 推荐节点布局

不要把所有 profile 都放在一台机器上。建议拆成多个浏览器节点。

一个实用起点：

- `browser-node-01`：维护热池 A 组 + 部分冷池
- `browser-node-02`：维护热池 B 组 + 部分冷池
- `browser-node-03`：维护热池 C 组 + 部分冷池

建议：

- 每台机器只承载 20 到 40 个长期 profile
- 每个 profile 固定账号，不混用
- 每个账号固定代理出口，尽量不要频繁切换 IP

## Profile 组织规范

每个账号必须有固定命名，避免后续混乱。

推荐命名：

- 账号标签：`gf-001`、`gf-002`、`gf-003`
- Profile 名：`flow-gf-001`
- 代理名：`proxy-gf-001`
- 节点名：`browser-node-01`

目录建议：

```text
/data/browser-profiles/
  flow-gf-001/
  flow-gf-002/
  flow-gf-003/
```

维护规则：

- 一个 profile 只登录一个账号
- 一个 profile 只绑定一个固定代理
- 不要在同一个 profile 上频繁切换账号
- 不要让多个节点共用同一个 profile 目录

## Token 自动回传链路

这个项目已经支持插件自动回传 token：

- 插件配置接口：`GET /api/plugin/config`
- 插件更新接口：`POST /api/plugin/update-token`

相关实现可以看：

- [admin.py](file:///Users/baolei/workspace/gflow-proxy-server/src/api/admin.py#L2053-L2206)

推荐流程：

1. 在 `Flow2API` 后台生成 `connection_token`
2. 在每个浏览器 profile 安装 `Flow2API-Token-Updater`
3. 插件配置回传地址和 `connection_token`
4. 浏览器里一旦登录态变化，插件自动把 `session_token` 推到 `Flow2API`
5. `Flow2API` 按邮箱自动新增或更新对应账号

这样后续的 token 管理会从“人工复制”变成“浏览器自动同步”。

## 首次建池步骤

### 阶段 1：基础设施

1. 部署 `Flow2API`
2. 配置统一对外 API Key
3. 配置管理后台密码
4. 配置验证码方案
5. 打开插件配置，生成 `connection_token`

### 阶段 2：浏览器农场

1. 准备 2 到 3 台浏览器节点
2. 每台节点创建一批固定 profile
3. 每个 profile 配置固定代理
4. 每个 profile 安装 Token Updater 插件

### 阶段 3：首批热池

1. 先只上线 10 到 20 个热池账号
2. 人工完成首次登录
3. 验证插件是否成功回传 token
4. 确认 `Flow2API` 里已自动出现这些账号
5. 给这些账号设置较保守并发

### 阶段 4：冷池登记

1. 再逐步登录冷池账号
2. 让插件自动同步到账号池
3. 默认先禁用或不纳入高频调用
4. 只在热池故障或扩容时启用

## Flow2API 里的推荐使用方式

### 调度

大号池建议优先使用：

- `call_mode = "polling"`

原因：

- 更适合均匀轮询热池账号
- 更容易观察某个账号是否异常
- 更适合热池分组轮换

### 并发

初始建议：

- 图片并发：每号 `1`
- 视频并发：每号 `1`

等跑稳后再逐步提到：

- 图片并发：每号 `2`
- 视频并发：仍建议先保持 `1`

### 启用策略

建议：

- 热池账号：`is_active = true`
- 冷池账号：按需启用

如果后面需要更严格控制，也可以只让热池在业务高峰期处于活跃状态。

## 推荐轮换策略

不要永远固定一批热池账号不变，建议分批轮换。

推荐策略：

- 每周检查热池健康度
- 每周从冷池提 2 到 5 个账号替换热池中异常账号
- 连续异常、频繁掉登录态的账号降级到冷池观察

这样可以降低某批账号被集中风控的概率。

## 日常运维 SOP

### 每日检查

每天看这几项：

- `/health`
- 后台的 token 活跃数
- 429 封禁数
- 即将过期账号数
- 当日错误率

### 每周检查

- 热池账号是否有持续失效
- 某组代理是否整体异常
- 某浏览器节点是否频繁丢登录态
- 冷池是否有足够可替补账号

### 故障恢复

如果某个账号失效：

1. 查它属于哪个 profile
2. 查 profile 所在节点
3. 检查代理是否异常
4. 打开浏览器确认是否掉登录
5. 必要时重新登录一次
6. 观察插件是否自动回传新 token

如果某个节点整体异常：

1. 暂停该节点对应热池账号
2. 从其他节点的冷池补位
3. 修复该节点网络、代理或浏览器环境

## 安全建议

- 管理后台不要直接暴露公网
- `connection_token` 单独保管，不要复用 API Key
- 浏览器节点和 API 网关尽量走内网或专用入口
- 定期备份数据库，防止账号映射关系丢失
- token 回传接口建议只允许受信任地址访问

## 你现在应该怎么开工

按最小可行方案推进，不要一口气上 100 个账号：

### 第一步

- 先把 `Flow2API` 跑起来
- 配好插件回传用的 `connection_token`

### 第二步

- 先建立 10 个热池账号
- 每个账号一个独立 profile
- 每个账号一个固定代理
- 每个 profile 装插件

### 第三步

- 验证 10 个号能自动回传 token
- 验证统一 API 调用是否稳定

### 第四步

- 再逐步把冷池账号纳入
- 不需要一次性全部上线活跃调度

## 你这套方案的最终目标

最终不是“手工导入 100 个 token”，而是形成下面的稳定机制：

- 账号有固定 profile
- profile 有固定代理
- 登录态变化能自动回传
- 热池稳定承载业务
- 冷池可随时补位
- 运维只需要处理异常账号，而不是维护所有账号

做到这一步，100+ 账号池才是真正可长期运转的。
